1. Overview

GBanking is a desktop application for managing bank accounts, transactions, recipients, categories and payment orders. Online banking uses FinTS/HBCI; PayPal accounts can be connected through the PayPal interface.

Review

See balances, transactions, account statements and bank messages in one place.

Organise

Filter, categorise, split and flag transactions or link movements between your own accounts.

Pay

Prepare supported transfers and standing orders and send them to the bank after review.

Analyse

Compare income, expenses, balance history and categories for selected accounts and periods.

Depends on your bank: GBanking enables an online feature only when the bank and account report support for the corresponding FinTS operation. Some buttons or order types may therefore be disabled.

2. Startup and tenants

A tenant is a self-contained set of data, similar to a separate GBanking user account. At startup, choose the language and tenant and sign in with its password.

  • New: Creates a tenant with a username and password.
  • Edit: Changes the username or password. The existing password is required for a password change.
  • Delete: Permanently removes the tenant and its data after verifying the password.
  • Demo: Creates a fresh sample data set. An existing demo is reset after confirmation.
  • File > Switch tenant: Closes the current data set safely and returns to sign-in.

By default, tenant data is stored below data/tenant/<UUID>. It contains the database, backups and account statements. A configured shared data directory is locked exclusively so that two running GBanking instances cannot write to it at the same time.

Networks and cloud folders: A network drive must reliably support file locks. Cloud-sync folders generally do not provide this guarantee. Close GBanking on the first computer and wait for synchronisation to finish before opening the data on another computer.

3. Data encryption and remaining risks

How protection is built

GBanking creates a random 256-bit data key for every tenant. That key encrypts data in AES-256-GCM containers. GCM prevents unauthorised reading and also detects an incorrect key or a modified encrypted file.

The tenant password does not encrypt every file directly. GBanking derives a wrapping key using PBKDF2-HMAC-SHA-256, a random salt and currently 210,000 iterations. This wrapping key protects the actual data key. Separate random nonces are used for the key and file content. tenants.properties contains the username and decryption metadata, but neither the password nor the unencrypted data key.

AreaAt restWhile GBanking is running
DatabaseEncrypted as gbanking.db.enc after a clean shutdown.Open as a readable gbanking.db because SQLite needs to work with it.
BackupsA *.gbbackup stores the database and account statements inside a fully encrypted container.The archive is written directly into the encrypted container.
Account statementsEither readable or encrypted as *.enc; changing the option also converts existing files.An encrypted statement is temporarily decrypted locally when opened.

At sign-in, the database is decrypted into a temporary file, checked and atomically made available as the working database. When switching tenants or exiting, GBanking closes SQLite, removes sidecar files, encrypts and verifies the result, atomically replaces the encrypted database and then deletes the working database. The session data key is overwritten in memory on a best-effort basis when the session closes.

If the configured data directory is not the default ./data, the readable working database stays locally below work/tenant/<UUID>/db, while the encrypted database remains in the selected data directory. Temporarily opened statements are stored below work/tenant/<UUID>/accountStatements and cleaned when switching tenants, exiting and signing in next time.

Password changes

The random data key remains unchanged when the password changes. GBanking wraps it with the new password and updates the encrypted database, managed backups and encrypted statements. The large contents therefore do not need to be encrypted again in full.

What encryption cannot prevent

  • Active session: Anyone who gains access to the computer, user account, memory or readable working database while the tenant is open may be able to read data. Encryption is not a replacement for operating-system security.
  • Crash or power loss: The readable database and SQLite sidecar files may remain. GBanking detects and validates this recovery state at the next start, but cannot prevent access in the meantime.
  • Account statements: Per-file encryption is optional. Even an encrypted statement briefly exists as a readable working copy when opened; after a hard crash, cleanup may not occur until the next sign-in.
  • Files outside the tenant: Exports, original imports, logs, diagnostic packages, environment and GUI settings, and the public bank directory are not automatically protected by tenant encryption.
  • Password strength: The implementation currently requires only a non-empty password. An attacker holding file copies can test weak passwords offline; key derivation slows this down but cannot prevent it.
  • External backup copies: Password changes update only containers inside GBanking's managed tenant folders. A backup copied elsewhere beforehand remains accessible with the password that protected it at the time.
  • Deletion: Files are deleted normally, not securely overwritten. SSDs, filesystem snapshots, recycle bins, backups or cloud version history may retain earlier readable or encrypted states.
  • Lost password: There is no back door or recovery key. Without a matching password, the data key cannot normally be unlocked.
Recommendation: Use a long, unique tenant password, lock and encrypt the operating-system drive as well, enable statement encryption when needed, and treat exports, logs, diagnostic packages and external backups as confidential financial records.

4. Using the interface

Open the main areas from Edit. Tables have a search field that covers their most important visible data. Checkboxes in the first column select multiple accounts, transactions, contacts or orders for a shared action. The checkbox in the table header selects or clears all visible rows.

  • Accounts/Transactions: Account-centred workspace with transactions and statements.
  • All accounts / All transactions: Tenant-wide overviews.
  • Orders, Categories, Address book, Bank accesses, Bank directory: Maintenance of the respective data.
  • View > Refresh: Reloads the current view. Show online accounts only hides offline accounts in account lists.

Many tables provide more commands on right-click. Column widths, sorting, window size, dividers and active tabs are retained for the next start.

5. Bank access and PayPal

Use Edit > Bank accesses to configure a bank or PayPal connection. A FinTS/HBCI access contains details such as bank code, user ID, FinTS address, protocol version and TAN procedure. During setup or update, GBanking fetches bank parameters (BPD), user parameters (UPD) and associated accounts.

  • Refresh BPD/UPD: Reloads capabilities and account information.
  • Show BPD/UPD: Displays the technical data supplied by the bank.
  • Bank messages: Retrieves messages for a FinTS access and shows text, type, date and other details.
  • PayPal: Uses API username, API password, API signature and email address. It retrieves the PayPal account and transactions; FinTS orders and bank messages do not apply.

PIN and TAN are requested in dialogs when needed. The procedure offered depends on the bank data, such as app approval, pushTAN, photoTAN or chipTAN USB. A chipTAN USB reader can be selected in Settings.

Review before approval: Compare the amount, recipient and the display in your TAN device or banking app. GBanking also shows any recipient verification requested by the bank before payment approval.

6. Accounts

In Accounts/Transactions, select an account on the left; account details, transactions and statements appear on the right. All accounts provides a tenant-wide list with full detail editing.

  • Online accounts are normally created when a bank access is set up or updated.
  • Offline accounts can be created manually, for example for cash or an account without online access.
  • Account name, type, currency and state can be maintained; GBanking warns before manual changes to linked online accounts.
  • The states active, inactive and ignore for analysis control use and reporting.
  • Account identifiers shows the technical mappings supplied by the bank.
  • The last retrieval status shows time, result or error and counts of new and pending transactions.

Check the desired online accounts and choose Run > Fetch transactions. GBanking retrieves the balance and transactions only where the access and bank report support.

7. Transactions

The transaction list includes the date, recipient or payer, purpose, category, type and amount. Pending transactions use a more subdued style. Filters can search by text, period, amount and other properties.

Details and manual maintenance

  • Online and imported transactions remain unchanged as historical bank records; a note and Review required flag can be maintained separately.
  • Manual transactions can be created, edited and deleted from the context menu.
  • A transaction can be divided into split transactions with separate amounts, categories and counter accounts. The sum and remaining difference are shown. Linked internal transfers cannot be split.
  • Selected transactions can receive a category, have it cleared or be processed again by all applicable rules.
  • An existing transaction can be used as a template for a transfer, scheduled transfer or standing order; its amount is copied as a positive value.

The context menu can also delete individual transactions or date ranges, release links between internal transfers, and import or export for the current account.

Deleting online transactions: Banks often provide older transactions for only a limited period. A deleted record may therefore no longer be available for retrieval.

8. Account statements and bank messages

The Account statements tab retrieves statements for the selected account, lists them and opens a statement with its associated desktop application. Details include period, statement number, format, file, size, retrieval time and receipt status.

Some banks require receipt acknowledgements. They can be sent directly or together with other work under Open actions. Retrieval and acknowledgements are available only when the bank supports them.

Bank messages have a separate tab in Bank accesses. FinTS messages can be retrieved and read in detail there.

9. Address book and current recipient logic

The address book contains both payment recipients and payers from incoming transactions. Contacts are created manually, by transaction imports and online retrieval, and when a payment order is saved. A contact can contain name, IBAN, BIC, account number, bank code, bank and a note.

Finding and using contacts

  • Search covers name, IBAN, bank, BIC, account number and bank code.
  • In order forms, select a contact from the address book list. Contacts used most often in payment orders appear first; equal usage is sorted by name.
  • A manually saved contact needs at least a name and either an IBAN or account number.

How GBanking avoids duplicates

GBanking first compares the IBAN or account number. IBAN matching is case-insensitive. If the other known data is compatible, the existing contact is reused. A contact that has not yet been used and has the same account identifier can be updated with the more complete incoming data instead of creating a duplicate.

Import data may fill in a missing bank name. For a German IBAN, GBanking can obtain the bank from the embedded bank code and the bank directory. A more readable spelling such as “Max Mustermann” may replace all-uppercase text without creating a new contact. Two explicitly different known bank names remain separate contacts so that potentially different identities are not merged.

Historical data remains stable

When a contact is already linked to an online/import transaction or a payment order, its identity fields are protected. An old transaction therefore remains linked to the same historical recipient. Such contacts cannot be deleted or freely changed in the address book.

If the recipient of a manual transaction changes, GBanking applies this rule: if the previous contact is linked only to manual transactions, it may be updated. If it is also historically protected, GBanking creates a new contact and reassigns only the manual transaction. Online and imported transactions are not reassigned.

Default contact

Several contacts may have the same IBAN or account number, for example after a name change. Use Default for this IBAN/account no. to select the preferred contact. Only one default can exist per account identifier; GBanking asks before replacing it.

During credit-card import, GBanking can associate an IBAN detected in the purpose text with a contact. It first uses the default contact. Without a default, the latest use in a transaction or order wins, followed by the most recently updated or newest contact.

Simple example: An older online transaction stays linked to “EXAMPLE COMPANY LTD”. If the same IBAN later arrives as “Example Company Ltd”, GBanking can improve readability. If actual identity details differ, new manual data uses a separate contact instead of rewriting history.

10. Categories and rules

Categories can be hierarchical, for example Household / Groceries. The Category rules tab defines automatic assignments.

  • Rules can apply to the current account, selected accounts or all accounts.
  • Conditions include period, amount range, recipient name, IBAN, account number and purpose.
  • Text conditions can be plain search text or regular expressions.
  • All conditions requires every condition; Any condition needs one match.

Rules are considered while new transactions are processed and can be reapplied to existing transactions with Apply categorisation. A manual category can also be assigned or cleared.

11. Payment orders

Orders provides tabs for SEPA transfers, scheduled transfers, standing orders and foreign transfers. The transfer tab may additionally offer real-time or urgent transfers. GBanking enables only order types supported by the selected account.

  1. Select the sender account and order type.
  2. Choose a contact from the address book or enter recipient data. For German account data, GBanking fills bank name/BIC and can suggest an IBAN from an account number and bank code.
  3. Enter amount, currency, purpose and, where required, execution date, interval or foreign-payment details.
  4. Save first stores the order locally.
  5. Run > Execute orders sends checked new or changed orders after PIN/TAN approval.

Scheduled-transfer and standing-order inventories are fetched through Run > Order inventory. If supported by the bank, changes and deletions are first queued and sent only with Execute orders. A queued deletion can be cancelled beforehand.

Each order type has an active list and an Archive. Previous, superseded, deleted or no-longer-listed versions remain traceable. The context menu shows the technical execution protocol and provides CSV import.

12. Running open actions together

Edit > Open actions groups pending online work: transaction retrieval, transfers, open scheduled transfers and standing orders, inventory retrieval, account statements and pending statement acknowledgements.

Check only the desired rows and select Run > Execute selected actions. GBanking groups work by bank access, asks for the required PINs and reports success, failure, cancellation or skipping for each action type.

13. Internal transfers

An internal transfer is a movement between two of your own accounts. GBanking can link matching counter-transactions by amount, date and counter account. Linked transfers are neutral in analysis, so moving money internally does not appear as both income and expense.

  • Run > Assign internal transfers: Finds and links existing counterparts.
  • Run > Create internal transfers: Creates selected missing counterparts in the target account.
  • Release internal-transfer link: Removes an incorrect link from the transaction context menu.

For export, select accounts with their checkboxes. Formats that can represent only one account require exactly one selection. CSV output also includes the account name, IBAN and account number. See the CSV format description for the full field list and examples.

Confidential files: Import sources and exports are outside tenant encryption. Store and transfer them securely.

15. Analysis

Under Analysis > Balances, choose all accounts, active accounts, online accounts or a custom selection. Periods include current month, last 30 days, last three months, current year, last 365 days, all time, since a date and a custom range.

Metrics show account and transaction counts, income, expenses, net flow, turnover, balance change and neutral internal transfers. A line chart shows balance history; a pie chart distributes income and expenses across categories.

Under Analysis > Categories, the same account and period selection is available together with a stacked bar chart showing income and expenses per category. Hovering over a category name or bar displays both amounts in a tooltip. An option enabled by default hides categories without turnover in the selected period. Accounts marked ignore for analysis are handled accordingly in both views. Each view retains its own selection for the tenant.

16. Bank directory

The bank directory contains public institution data such as bank name, short name, BIC, bank code, city, status and validity dates. Search helps verify bank data; GBanking also uses the directory to fill bank names and BIC/bank codes for contacts and orders.

The data comes from bundled institution files and is separate from personal tenant data. If the directory is unavailable, GBanking can continue after a warning with reduced bank-data lookup.

17. Settings

  • Program settings: Visible technical values including logging, chipTAN USB reader and optional account-statement file encryption.
  • Recognition patterns: Search text and regular expressions for special transactions, cancellations and account-specific exclusions. Change these only when you understand their effect.
  • Environment-specific settings: Data directory, import-properties directory and separate last-used import and export directories.

Tenant-specific settings are held in the database and synchronised with import properties. Installation-local values are stored in properties/env.properties; window and layout values remain in properties/gui.properties. Changing statement encryption converts existing statement files accordingly.

18. Backup, restore, update and diagnostics

Backups

Before opening an existing database, GBanking creates an encrypted opening backup and checks whether weekly, two-monthly and yearly backups are due. File > Create backup adds a manual *.gbbackup. Backups include the database and account statements.

File > Restore backup replaces the current tenant state after confirmation. A recovery-point backup of the current state is created first. The database and statements from the selected backup are then validated and swapped in.

Updates

About > Check for updates searches for a newer GBanking version. In an extracted release distribution with bin and lib directories, the application can download the matching package, verify checksum and signature, start the installer and exit GBanking.

Logs and diagnostics

About > Open log directory opens local logs. Create diagnostic package collects relevant diagnostics and logs in a ZIP archive. Confidential identifiers are masked where designed, but review the contents before sharing.
