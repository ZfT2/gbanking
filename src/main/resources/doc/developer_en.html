1. Getting started

GBanking is a Java desktop application. It is built with Maven, targets Java 17 and uses JavaFX 21 for its user interface. Production data is stored in SQLite; FinTS/HBCI, Enablebanking and PayPal are the principal external banking integrations.

Prerequisites

  • JDK 17 or newer and a suitable Maven installation.
  • Git; JavaFX tests on Linux also need a graphical session or xvfb-run.
  • Never put real credentials into tests, logs, fixtures or commits.
mvn clean install

# one test or test class
mvn -Dtest=ServiceRegistryTest test

# distribution archive for a target platform
mvn -Pwindows clean package
mvn -Plinux clean package
mvn -Pmac clean package

The application entry point is de.zft2.gbanking.GBanking. It uses AppPaths to determine the application directory and launches GBankingGui. Production code is below src/main/java, resources below src/main/resources, and tests mirror the package structure below src/test/java.

First orientation: The quickest way to understand a business feature is usually to follow it from an OverviewPanel, through its service, to the DAO or repository. Tests next to these classes often document edge cases more precisely than the UI does.

3. Application and session lifecycle

  1. GBanking.main sets gbanking.baseDir and launches JavaFX.
  2. GBankingGui.start restores environment and GUI settings and initializes file chooser state.
  3. TenantLoginDialog authenticates the tenant, acquires its file lock and prepares the working database.
  4. DbRuntimeContext binds the database, data and account-statement directories to a new session generation.
  5. The main window is assembled. OverviewPanelFactory creates the initial ACCOUNTS_TRANSACTIONS page on first use.
  6. GBankingService.setup starts maintenance of the institute directory; further services are obtained from ServiceRegistry.

During a tenant switch, backup restore or shutdown, the GUI is disabled. BackgroundActionCoordinator waits for database-bound background actions or cancels them after an explicit user choice. Only then are SQLite, temporary files and the tenant session closed. Services, caches, GUI context and lazily created panels are reset between tenants.

Important invariant: A background thread must never continue against an old database session after a tenant switch. Start database work through BackgroundActionCoordinator or DbRuntimeContext.startBackgroundThread, and never bypass these coordinators when implementing a lifecycle transition.

TenantDatabaseLifecycleManager decrypts the database before opening, detects recovery states and encrypts it again after closing. See the final chapter of the user manual for the protection model and its limitations.

4. Persistence

Data locations and sessions

TenantPaths describes a tenant's database, encrypted database, backup and account-statement directories. When an external data directory is configured, the readable SQLite working file may live separately below work/tenant/<UUID>/db. Domain code must use TenantPaths, DbRuntimeContext and AppPaths rather than assembling these paths itself.

DbConnectionHandler manages exactly one active DbSession. A session owns the JDBC connection, JdbcOperations, repository catalog and per-session setup markers. It cannot be reused when its generation no longer matches DbRuntimeContext.

Access layers

ComponentPurposeCore functions
DBControllerPublic facade for standard CRUD and domain-specific aggregate operations.getInstance, executeInTransaction, recipient, category, account and booking operations
DbExecutorGeneric read and write operations for DAOs.getById, getByIdFull, getAll, getAllByParent, insertOrUpdate, delete
DaoRepository<T>Uniform contract for each DAO type.findById, find, findAll, executeWrite, delete
DaoRepositoryCatalogMaps DAO classes to generic, read-only, securities or specialized repositories.Registration while creating a DbSession
StatementsConfigAssociates each DAO with a mapper, relation logic, view and SQL statements.StatementType, ResultType, metadata lookup
JdbcOperationsLow-level JDBC operations with prepared statements and result mapping.Query, update and batch helpers

getById and getAll do not normally load complete relations. Their Full variants select additional columns and let the matching StatementsLogic resolve relationships. This distinction avoids unnecessary object graphs in list views.

SQL and mapping

  • src/main/resources/sql/dml contains named queries and write statements. SqlTemplateRepository reads and validates the templates.
  • DaoSqlStatements exposes frequently used keys as constants.
  • Mappers below db.dao.mapper read result sets and bind entity values. Relation logic below db.dao.logic completes dependent objects and many-to-many tables.
  • Securities DAOs use StockDaoMetadata, allowing many tables to share one StockDaoRepository.

Transactions and side effects

DBController.executeInTransaction or DbExecutor.withDbTransaction marks a business transaction boundary. DbTransactionManager serializes database access with a fair lock. Nested calls join the outer transaction; a failing inner call marks the whole transaction rollback-only. If a commit outcome or connection state is uncertain, the session is quarantined so processing cannot silently continue on questionable state.

Rule: Group related writes in one service method and one explicit transaction. File or in-memory side effects that must be reverted on rollback should use the persistence layer's existing rollback mechanisms.

Schema and migrations

The baseline is versioned below sql/ddl/0.1.0; later directories contain incremental scripts. DbMigrationRunner reads hidden settings to determine pending versions, applies them in order and records schema and application versions. Migrations run with auto-commit, so each script must be designed to fail clearly and be safe in its intended state. DbConnectionHandler then checks foreign keys and database integrity.

The public institute directory is a separate institute.db file. It is prepared and attached to the tenant connection as schema institute_db. Do not treat changes to tenant data and the institute directory as one domain transaction.

Adding a persistent type

  1. Add the DAO and any enums; define identity, nullability and state fields.
  2. Add DDL as a new versioned migration; never reinterpret an already released migration.
  3. Add DML keys and implement the mapper and, when needed, StatementsLogic.
  4. Register the type in StatementsConfig and DaoRepositoryCatalog. Use the read-only repository for read-only types.
  5. Add repository/controller tests for CRUD, relations, rollback, foreign keys and migration.

5. Application functions and services

Services implement business use cases. They own validation, provider selection, transaction boundaries and the order of persistence steps. GUI classes should collect inputs and present results, not reimplement the same rules.

Creation and lifetime

Registered classes implement the empty Service marker interface. ServiceRegistry.getService invokes a no-argument constructor and caches one instance per service class. Constructors obtain dependent services from the registry as well. Tenant switching and backup restore clear the registry. Tests can use setService, removeService and resetServices to inject doubles and isolate state.

AbstractDbService supplies DBController.getInstance("."). In this context the dot means “use the database activated by DbRuntimeContext”, not “open an arbitrary new tenant database”.

Core functions

  • AccountTransactionService.retrieveAccountTransactionsWithResult selects PayPal, Enablebanking or FinTS from the configured bank access and unifies persistence afterwards.
  • BankingCapabilityService evaluates account type, access, BPD, UPD and announced business transactions. The GUI queries it before offering online actions.
  • MoneyTransferExecutionService encapsulates security-sensitive execution, bank responses and status transitions; FinTsStatusProtocolService and the protocol evaluator interpret feedback.
  • StockPortfolioService is the main facade for portfolio views, transactions, prices, income, transfers and settlement-account bookings.
  • GBankingService.postRetriveActions links rebookings and applies category rules after retrieval.

External adapters

HbciSessionRunner limits the lifetime of HBCI handlers, passports and secrets. GBankingHBCICallback connects PIN/TAN dialogs and status to the GUI. Enablebanking has separate classes for OAuth authorization, callback server, API client and paginated transaction retrieval. PayPal encapsulates SOAP transport, account and transaction services. Provider-specific DTOs should remain in these adapter packages and be translated into GBanking domain objects before reaching services and persistence.

Security rule: Never store or log PINs, TANs, OAuth keys or full account identifiers without filtering. Keep secrets alive for the shortest possible time, clear them after use and rely on the existing masking and callback classes.

6. GUI

Navigation and pages

GBankingGui owns the main window and coordinates application-wide actions. GBankingNavigationBar combines menus and quick navigation. Each main page is represented by a PageContext. OverviewPanelFactory maps that enum to an OverviewBasePanel, creates it on first access and caches it for the current tenant session. refreshOnShow refreshes data when the page is shown again.

GUI packageContents
gui.panel.overviewMain pages for accounts/transactions, portfolios, orders, categories, recipients, administration and analysis.
gui.panel.account, transaction, stock, moneytransfer, etc.Domain-specific list, detail and form panels.
gui.dialogModal dialogs; subpackages group tenant, FinTS, rebooking and securities dialogs.
gui.progressJavaFX tasks and progress windows for file and online operations.
gui.component, gui.utilReusable tables, columns, fields, styles, shortcuts and FX-thread helpers.

Reusable patterns

  • AbstractFilterableTablePanel<T> wires a master list, filtered and sorted views, search field, selection and context menu. Subclasses supply matchesFilter and their columns.
  • AbstractTitledFormPanel and FormGridHelper standardize forms. DetailFormEditMode consistently toggles fields and buttons between viewing and editing.
  • MasterContentPane and DetailListPane implement master-detail layouts. GuiLayoutState persists window, table and SplitPane state.
  • KeyboardShortcutDispatcher registers find, save, cancel and refresh actions for the active area.
  • Text comes from messages_de.properties and messages_en.properties through BaseMessagesBean.getText; do not hard-code visible text in Java.

Threads and refresh

Read or change JavaFX nodes only on the FX Application Thread. Long-running network, file and database operations belong in a Task. BaseGui.startBackgroundTask delegates to BackgroundActionCoordinator. Its default DATABASE scope binds the current tenant session; use INDEPENDENT only for truly tenant-independent work. Completion handling and visible updates return to the FX thread.

Refresh pattern: After a successful save, use the service result, reload the affected list and restore selection deliberately. Do not assume that a cached OverviewPanel automatically observes changes in another panel.

Adding a main page

  1. Add a value to PageContext and update both message bundles.
  2. Implement an OverviewBasePanel, use setPageContext and setOverviewContent, and define refreshOnShow.
  3. Add its mapping to OverviewPanelFactory.createOverviewPanel.
  4. Connect a menu or navigation action to GBankingGui.activateOverview.
  5. Add factory/navigation and panel tests; test JavaFX code on the correct thread with JavaFxTestSupport.

7. Core flows

Retrieving account transactions

  1. The account view asks BankingCapabilityService whether an update is supported and starts a database-bound task.
  2. AccountTransactionService resolves the bank access and selects FinTS, Enablebanking or PayPal.
  3. The adapter returns balance, booked and, when available, pending transactions as GBanking objects.
  4. A DB transaction updates the balance, sources, duplicate state, new/pending bookings and retrieval status.
  5. GBankingService then links rebookings and applies category rules.
  6. The GUI consumes the structured result, clears secrets and refreshes affected views.

Executing a payment order

The GUI validates whether input is allowed and obtains confirmation. The money-transfer service persists the order and delegates bank execution to MoneyTransferExecutionService. Protocol services and evaluators translate feedback into an unambiguous local state. An unknown commit or bank response must never be treated as automatically safe to retry.

Portfolios and securities

StockPortfolioFinTsService imports bank holdings and reconciliation data. StockPortfolioService then combines portfolios, positions, transactions, security master data, prices and settlement accounts into summary records for the GUI. Manual buys, sells, income and transfers write all related legs and bookings in one transaction.

File import

FileTransferCoordinator selects a file and target, creates the matching import task and opens the progress dialog. Parsers and import beans live below file.imp; assignment, duplicate detection and persistence are separated. The coordinator refreshes affected OverviewPanels only after successful completion. Exports follow the same pattern using file.exp.

8. Cross-cutting concerns

  • Localization: Messages supports German and English. Every new visible key belongs in both properties files; a missing key otherwise appears as the key itself.
  • Logging: Use Log4j2 and parameterized messages. SensitiveDataMasker and HbciLogMessageSanitizer protect common secrets; review new logging paths for financial and authentication data.
  • Settings: GUI/environment state uses RestoreHandler and EnvironmentOptions; domain settings use typed SettingsStore entries in the database.
  • Cancellation: Longer loops and I/O paths should observe CancellationSupport. A cancelled operation must not leave a partial business change.
  • Updates: The update package separates release metadata, download, checksum, signature verification, extraction and installer launch. Do not bypass verification steps.
  • Help documents: HTML files live below src/main/resources/doc. Every relative link must appear in GBankingGui.HELP_DOCUMENTS so the target is copied to the temporary help directory.

9. Extending a feature

Start with the business use case, not the button. A typical vertical change follows this order:

  1. Define behavior: Describe input, result, failure cases, tenant scope and atomic boundary.
  2. Model/persistence: Reuse existing DAOs and queries. Add schema, migration, mapper and repository only when new persistent state is required.
  3. Service: Coordinate validation, transaction and provider/file adapters in a testable service method. Return structured results instead of GUI callbacks.
  4. GUI: Bind input, invoke the service directly for short work or in a task for long work, display useful errors and refresh views.
  5. Localization and help: Update German and English text together, as well as the user manual and developer documentation when architecture changes.
  6. Tests: Cover service edge cases first, then persistence integration and focused GUI tests. Run the complete build before handing off.
Code review questions: Is the transaction boundary correct? Are secrets and personal data kept out of logs? Can an old background task write into a new tenant? Are both languages complete? Could an uncertain external order be retried automatically?

10. Tests, build and troubleshooting

Test types

  • Unit tests use JUnit 5 and Mockito. ServiceRegistry.setService can inject test doubles.
  • Persistence tests open a database in a temporary directory and close it through DBController.resetConnection or existing test helpers.
  • JavaFX tests create controls and run assertions through JavaFxTestSupport.runFx or callFx.
  • Migration, integrity, import and encryption tests pay particular attention to failure and recovery paths.

Maven runs tests with target/test-working as the working directory, software rendering and headless AWT. Test code must not assume that the repository is the current working directory. CI runs JavaFX tests on Linux with xvfb-run -a mvn -B clean test.

Suggested verification

# fast domain cycle
mvn -Dtest=AffectedServiceTest test

# full verification
mvn clean test

# complete build
mvn clean install

For database failures, inspect the original log event first; follow-up errors may come from a deliberately quarantined session. For stale views, verify that the service succeeded, completion runs on the FX thread and the correct cached panel was refreshed. During tenant switching, active actions and the session generation are the first places to inspect.

Test data: Never use the production gbanking.db or a real tenant directory as a test target. Temporary directories and existing fixtures keep tests reproducible and prevent data loss.

11. Suggested onboarding path

  1. Application shell: Read GBanking, GBankingGui.start, PageContext and OverviewPanelFactory.
  2. A small domain: Trace categories or recipients from the OverviewPanel through the service, DBController, repository, mapper and SQL.
  3. Transactions: Study DbExecutor, DbTransactionManager, DbSession and their tests.
  4. Online flow: Follow transaction retrieval through AccountTransactionService, one provider adapter and the post-processing services.
  5. Complex domain: Then read StockPortfolioService or MoneyTransferExecutionService; both demonstrate atomic multi-table workflows and structured results.
  6. Lifecycle/security: Review TenantDatabaseLifecycleManager, BackgroundActionCoordinator and the encryption/backup tests.
A good first change: Extend a small, already tested list or form feature. This exercises localization, service access, refresh, a GUI test and the full build without immediately touching banking protocols or encryption.
